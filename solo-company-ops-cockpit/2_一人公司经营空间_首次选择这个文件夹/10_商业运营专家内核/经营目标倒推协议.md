# 经营目标倒推协议

本协议把“算清账 → 保本线 → 目标利润 → 盈利营业额与交付目标 → 现金保底与销售目标 → 漏斗任务 → 当前差额 → 本周唯一动作 → 周复盘重新校准”固化为产品工作流。公式、哈希和任务数量全部由 `90_系统设置_不用先看/创业算账引擎.js` 计算；AI 只负责追问、识别依据、解释结果、判断瓶颈和主持确认，不得自由心算或修改确定性数字。

## 两类记录与权限

- `20_经营数据/经营目标/目标方案/*.md`：`record_type: business_target_plan`。用户在创业算账页查看摘要并确认后创建；AI 永久只读，不得新建、编辑、覆盖或停用。
- `20_经营数据/经营目标/行动计划/*.md`：`record_type: operating_action_plan`。AI 读取当前有效目标后，通过确定性脚本生成草稿。用户直接要求保存时，通过业务校验后直接新增；AI 主动提议保存时才需一次短预览与确认。禁止 Edit 或覆盖旧记录。
- 目标方案绑定 `calculation_id + source_input_hash + target_input_hash`；行动计划绑定 `target_plan_id + target_input_hash + breakdown_input_hash`。任一上游哈希变化，旧下游记录保留历史但立即退出当前读取，不得复制旧数字继续使用。
- 两类记录都必须保存确定性 `input + result` JSON 数据块并使用 `hash_algorithm: fnv1a64`。写回守卫必须复算并深度比对结果；只校验 frontmatter 或听信 AI 声明不算通过。

## 目标方案：固定双闭环

目标月份按自然月。目标利润指支付全部成本和创业者合理工资后，公司仍要赚到的钱；目标现金增加可选，默认 `0`。创业者合理工资缺失时不得生成完整利润线或现金线。

利润交付线由 `calculateBusinessTargetPlan(input)` 计算：

```text
固定需要 = 固定经营成本 + 创业者合理工资
保本营业额 = 固定需要 ÷ 贡献毛利率
盈利营业额 =（固定需要 + 目标利润）÷ 贡献毛利率
目标交付量 = ceil（固定需要 + 目标利润）÷ 单位贡献
产能占用率 = 目标交付量 ÷ 最大稳定交付量
```

存在单位模型时，以整数目标交付量对应的可执行盈利营业额为主；理论盈利营业额只作折叠参考。单位贡献小于等于零时不得生成伪目标：允许保存一份带 `planStatus: blocked_unit_economics` 与 `blockers` 的诊断记录，但盈利、交付、实收和成交目标必须保持 `null`，唯一动作只能先处理定价或成本。目标交付量超过最大稳定交付量时必须标记不可行，不得继续扩大获客任务。

销售收款线由同一函数计算：

```text
预计变动现金成本 = 目标交付量 × 单位直接成本
刚性现金需要 = 已填未来刚性支出
              或 固定经营成本 + 创业者合理工资
最低实收目标 = 刚性现金需要
             + 预计变动现金成本
             + 目标现金增加
月成交目标 = ceil（最低实收目标 ÷ 平均每单本月实收）
```

缺少平均每单本月实收时，只显示最低实收金额，不伪造成交单数。销售目标、实际收款、确认收入、成交单数和交付量必须独立记录；订阅、储值、里程碑等业务不得默认一笔销售等于一个交付单位。

目标记录在写入与读取时都用 `validateBusinessTargetPlanRecord(record, expectedSourceInputHash)` 复算。目标页保存前必须重新读取来源核算，确认它仍为 `business_calculation + confirmed`，且 `calculation_id + input_hash` 与目标输入一致。

## 行动计划：确定性倒推

`/target-breakdown` 固定读取最新有效核算、最新有效目标方案和与之匹配的最新行动计划。每轮只问 1—3 个问题，按需确认：

1. 当前累计实际实收、成交单数、确认收入和交付量。
2. 剩余有效经营日。
3. 触达→回应、回应→讨论、讨论→报价、报价→成交的转化率，以及它们是 `historical`、`user_estimate` 还是 `mixed`。
4. 必要时确认 1—3 个主要渠道及目标占比。

AI 收集普通语言输入后，必须调用只读脚本 `.claude/skills/commercial-operations-expert/scripts/target-breakdown.js`。脚本使用 `calculateOperatingBreakdown(input)` 逐级向上取整：

```text
所需报价 = ceil（月成交目标 ÷ 报价成交率）
所需讨论 = ceil（所需报价 ÷ 讨论报价率）
所需回应 = ceil（所需讨论 ÷ 回应讨论率）
所需触达 = ceil（所需回应 ÷ 触达回应率）
每日任务 = ceil（剩余任务 ÷ 剩余有效经营日）
```

所有“剩余任务”先扣除本月已经完成的对应事实，最小为 `0`。多渠道占比与周权重分别必须合计 `100%`；不得用四舍五入后看似 100% 的值掩盖原始输入错误。冲刺系数可选、默认 `1.00`，使用时单独显示，不得把隐藏冲刺量混入基础目标。

## 转化率未知与七天校准

- 有真实历史数据：记录分子、分母和观察周期，标记 `historical`。
- 没有历史但用户能给出粗略判断：让用户明确确认，标记 `user_estimate`；不得改写成行业事实。
- 用户完全不知道：进入 `seven_day_calibration`。七天内只记录触达、回应、讨论、报价、成交的分子与分母，不生成伪精确漏斗目标，不调用行业默认转化率。
- 校准数据不足时，唯一动作必须是完成七天校准；获得真实数据后再生成新行动计划，旧假设保留历史但不继续冒充当前依据。

## 当前差额与唯一动作

完整目标树保存在行动计划后台，但对用户只突出一个“本周先做”。`calculateOperatingBreakdown(input)` 必须按以下顺序生成 `uniqueAction`，AI 只能解释或让用户纠正输入，不能绕过优先级改选：

1. 单位贡献不为正：先处理定价或成本。
2. 盈利交付目标超过产能：先处理价格、成本、交付方式或产能；不得扩大获客目标。
3. 现金缺口危及经营：先处理收款。
4. 其余情况选择归一化差额最大的漏斗环节。
5. 数据不足：执行七天校准动作。

行动记录至少包含四类实际进度、四类剩余差额、转化依据、渠道与周权重、冲刺系数、漏斗任务、每日任务、校准状态、最大断点和唯一动作。所有数字必须逐字来自脚本输出。

## 行动计划写回

1. 生成拆解前重新读取当前目标与来源核算；目标缺失、哈希失配、单位贡献不为正或产能不可行时，按引擎状态停止不适用的漏斗扩张。
2. 只读脚本输出完整 JSON 后，AI 用普通中文展示“【目标拆解草稿】”，注明真实历史、用户估计或七天校准，不改任何确定性数字。
3. 用户采用或修正输入后，重新调用脚本；不得在旧结果上手改。
4. 需要保存时，新建 `20_经营数据/经营目标/行动计划/<action_plan_id>.md`。实际写入的 JSON 数据块固定保存 `{ "input": <deterministicInput>, "result": <完整 operating_action_plan envelope> }`，不能只保存 `preview`。用户不需核对技术哈希、脚本命令或整份 Markdown；用户直接要求保存时就是授权。AI 主动提议保存时，短预览只列目标路径、关键变化与唯一动作。
5. 守卫对实际 Write 调用同一确定性脚本并使用 `validateOperatingActionPlanRecord(record, expectedTargetInputHash)` 复算，拒绝旧目标、旧业务哈希、篡改数字、隐藏冲刺系数、非法占比、越权路径或 Edit。这些是数据资格校验，不是聊天排版或技术令牌校验。
6. 写后复读目标与行动记录，再次核对哈希及唯一动作；只有复读通过才可输出“【已写入看板】”。

## 周复盘重新校准

每周复盘更新本周实际分子、分母和四类进度，区分新事实与旧假设。若核算或目标输入已改变，应先生成新目标方案，再重新拆解；不得覆盖旧目标或旧行动。有效 `operating_action_plan` 的唯一动作优先于旧 `finance_ai_insight` 建议；不存在有效目标方案时，首页和原经营流程保持现状。
